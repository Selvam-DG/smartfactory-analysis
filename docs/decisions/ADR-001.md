# ADR-001: Why PostgreSQL over MongoDB

**Date:** 2026-05-01  
**Status:** Accepted

## Context

SmartFactory Reliability Analytics needs to store machine sensor readings, production records, breakdown logs, maintenance schedules, and analytics-ready KPI tables. The project requires reliable joins across machines, dates, production shifts, breakdown events, maintenance records, and prediction outputs.

The database must support raw data ingestion, idempotent loading, SQL-based transformations, dashboard queries, and future extensions such as semantic search or AI-assisted maintenance recommendations.

## Decision

Use PostgreSQL as the primary database instead of MongoDB.

## Rationale

- PostgreSQL provides strong relational modeling for structured industrial data such as machines, production records, breakdowns, maintenance schedules, and KPI tables.
- ACID compliance is important for reliable ETL execution, idempotent loads, and analytics refreshes where partial writes or duplicated records should be avoided.
- SQL is a natural fit for calculating OEE, MTBF, MTTR, downtime Pareto, maintenance compliance, and dashboard-ready aggregations.
- PostgreSQL is widely used in enterprise environments, including German industrial and manufacturing companies, making it more relevant for data engineering interviews.
- PostgreSQL can support future AI/RAG extensions through `pgvector`, allowing the project to evolve toward maintenance knowledge search or failure-recommendation features without changing the core database.

## Alternatives considered

### MongoDB

MongoDB was considered because sensor data can sometimes be semi-structured and document-oriented databases are flexible for changing data shapes.

It was rejected for this project because the core data model is highly relational. Dashboard and KPI logic require frequent joins, aggregations, date filtering, grouping, and consistency checks. Implementing OEE, MTBF, MTTR, and Pareto calculations would be less transparent than using SQL.

### SQLite

SQLite was considered for simplicity and local development.

It was rejected because the project is intended to demonstrate production-style data engineering practices. PostgreSQL better represents the type of database used in real analytics platforms and supports schemas, indexes, concurrent access, and Docker-based deployment more realistically.

### DuckDB

DuckDB was considered for analytical performance on local files.

It was rejected as the primary database because the project needs to demonstrate an application-style architecture with persistent raw and analytics schemas, ETL loading, dashboard access, and database service deployment through Docker Compose.

## Consequences

### Positive consequences

- Clear separation between `raw` and `analytics` schemas.
- Strong support for SQL transformations and dashboard queries.
- Better demonstration of data engineering and analytics engineering skills.
- Easier implementation of idempotent loads using unique constraints and upsert logic.
- Future compatibility with advanced PostgreSQL extensions such as `pgvector`.

### Negative consequences

- Slightly more setup complexity than SQLite or flat files.
- Requires running a PostgreSQL service locally or through Docker.
- Requires careful schema and index design to keep dashboard queries fast.
- Less flexible than MongoDB for highly irregular or deeply nested source data.

## Review date

Review this decision if raw sensor data volume exceeds 50 million rows, if real-time streaming ingestion is added, or if the project requires storing highly variable nested machine event payloads that do not fit a relational model cleanly.
