# ADR-004: Why Docker Compose over Kubernetes

**Date:** 2026-05-01  
**Status:** Accepted

## Context

SmartFactory Reliability Analytics needs a reproducible local development and demo environment. The system includes PostgreSQL, data generation, ETL execution, ML prediction, and a Streamlit dashboard. Optional Airflow orchestration may also be included.

The project is intended for portfolio demonstration and interview discussion, not production deployment across a distributed cluster.

## Decision

Use Docker Compose for local orchestration instead of Kubernetes.

## Rationale

- Docker Compose is simpler and more appropriate for running a small multi-service project locally.
- It allows PostgreSQL, Streamlit, ETL, ML, and optional Airflow services to be started with clear commands.
- It keeps the project easy for recruiters, reviewers, and interviewers to run on a laptop.
- Kubernetes would add operational complexity that is not required for the current project scope.
- Docker Compose still demonstrates containerization, service configuration, environment variables, and reproducible deployment basics.

## Alternatives considered

### Kubernetes

Kubernetes was considered because it is widely used for production-grade container orchestration.

It was rejected because this project does not currently require horizontal scaling, service mesh, cluster scheduling, autoscaling, ingress management, or high availability. Adding Kubernetes would make the project harder to run locally and could distract from the main data engineering and analytics goals.

### Running everything directly on the host machine

Running PostgreSQL, Streamlit, ETL, and ML directly on the host was considered for simplicity.

It was rejected because local host setup can vary across machines. Docker Compose provides a more reproducible environment and reduces dependency conflicts.

### Cloud deployment

A managed cloud deployment was considered as a future extension.

It was rejected for the base version because the project should be easy to run locally without cloud credentials, cost, or infrastructure setup.

## Consequences

### Positive consequences

- Easy local setup using `docker compose up`.
- Clear service definitions for PostgreSQL, Streamlit, ETL, and optional Airflow.
- Good balance between realism and simplicity.
- Lower operational overhead than Kubernetes.
- Better reviewer experience for a public portfolio project.

### Negative consequences

- Docker Compose is not a full production orchestration solution.
- No built-in autoscaling, rolling deployments, or cluster-level resilience.
- Secrets management is basic and relies on local environment variables.
- High availability and multi-node deployment are outside the current architecture.

## Review date

Review this decision if the project is deployed to a shared production environment, requires multiple users, needs autoscaling, requires high availability, or grows beyond a local portfolio/demo architecture.
